# Issue 关联提交

仅当用户明确要求执行 `commit` 或“提交”时使用本 Skill。完成本地提交，但不要推送、合并、发布或更新 Issue 状态。

## 不可变规则

- 先遵守仓库及目标路径最近的 `AGENTS.md`，包括环境检查、任务合同、验证和文档提交规则。
- 只暂存本次任务范围内的文件。不得使用 `git add .`、`git add -A` 或借机纳入其他人的改动。
- 若已有暂存内容无法明确归属于本次任务，停止并让用户确认范围；不要擅自取消暂存或覆盖改动。
- API 查询失败不等于没有匹配 Issue。只有成功查询完全部候选后，才可创建 Issue。
- 不在命令、日志、回复、提交信息、URL 或生成文件中显示 API Token。
- 除创建 Issue 时将 Token 对应的当前用户设为负责人外，不通过 API 更新 Issue 状态、添加评论、负责人、标签或里程碑。

## 1. 确认提交范围

1. 运行仓库要求的只读环境检查。
2. 检查 `git status --short`、暂存差异、未暂存差异和未跟踪文件。
3. 根据当前任务上下文、实际差异及用户指令列出本次提交文件。无法可靠区分不同任务的改动时，停止并请用户确认。
4. 读取适用于这些文件的仓库规则。文档默认不提交，除非用户明确要求或仓库规则另有规定。
5. 在访问 IssueFlow 前，不要暂存或提交。

## 2. 连接配置前置检查

配置文件固定为仓库根目录的 `issue/config.toml`，字段格式为：

```toml
API_BASE_URL = ""
API_TOKEN = ""
```

按以下顺序处理：

1. 检查根 `.gitignore` 是否精确忽略 `/issue/config.toml`。若未忽略，使用最小改动添加该规则，不改写用户的其他忽略项。
2. 使用 `git check-ignore issue/config.toml` 验证规则生效。
3. 若 `issue/config.toml` 已被 Git 跟踪，立即停止并提醒用户先安全移除跟踪；不要读取 Token、不要自行执行 `git rm --cached`。
4. 若文件不存在，创建 `issue/` 和配置文件，写入上述两个空字段，然后停止任务，要求用户填写连接配置。
5. 若 `API_BASE_URL` 或 `API_TOKEN` 不存在，补充对应空字段后停止任务，要求用户填写。
6. 若任一字段为空、只有空白、重复、不是 TOML 字符串或格式无法可靠解析，停止任务并指出问题；不得猜测配置值。
7. `API_BASE_URL` 必须使用 HTTPS，且不得包含用户信息、查询参数或片段；请求时去除末尾 `/`，再拼接下文列出的接口路径。
8. 配置有值后，仅在内存或当前进程变量中使用。不得打印 Token、启用 Shell trace、将 Token 写入临时日志或加入 Git。

配置缺失分支是本次运行的终点。用户填写后必须重新明确要求提交，才重新开始流程。

## 3. IssueFlow API

基础地址读取 `issue/config.toml` 中的 `API_BASE_URL`。认证头为：

```http
Authorization: Bearer <API_TOKEN>
```

Token 不得放入查询参数。先调用以下接口验证认证并取得 Token 对应的当前用户；`401` 或 `403` 时停止并要求用户检查 Token 或权限：

```http
GET /api/auth/me
```

从成功响应中读取当前用户的 `id`，后续创建 Issue 时将该 ID 作为唯一负责人。若响应没有可用的用户 ID，停止创建并报告响应结构不符合预期；不得创建无人负责的 Issue，也不得猜测用户 ID。

错误响应结构为：

```json
{
  "error": {
    "code": "API_TOKEN_INVALID",
    "message": "Invalid API token",
    "requestId": "req-1"
  }
}
```

API 请求失败时向用户报告状态码、错误码和 `requestId`，但不得包含 Token。`401` 表示 Token 无效或过期，`403` 表示权限不足，`409` 表示数据冲突。遇到网络错误、超时、`429` 或 `5xx` 时停止；不把失败降级为“无匹配 Issue”。

### 查询开放和待验收 Issue

使用：

```http
GET /api/issues?state=OPEN&page=1&pageSize=100&sort=updatedAt&order=desc
```

该 API 的 `state=OPEN` 会同时返回 `OPEN` 和 `AWAITING_ACCEPTANCE`。仍需检查响应中的实际状态，只保留这两种状态。逐页查询，直到最后一页；不得只检查第一页。

必要时获取单个 Issue 的完整内容：

```http
GET /api/issues/{id}
```

结合以下证据判断是否符合当前更改：

- 本次提交的实际差异和目标；
- 改动路径或业务模块；
- Issue 标题、正文、目标和验收标准；
- Issue 描述的问题或需求是否与变更产生的行为一致。

不得仅因关键词相同就关联。若多个候选同等相关，列出编号和标题并停止，让用户选择；不要自动挑选。

### 创建 Issue

成功完成全部查询且没有匹配项时，自动创建 Issue。调用前只向用户展示拟创建的标题，不展示正文，也不等待二次确认。

提交类型与 Issue 标题固定前缀映射如下：

| Commit 类型 | Issue 前缀 |
| --- | --- |
| `fix` | `[bug]` |
| `feat` | `[feature]` |
| `docs` | `[docs]` |
| `refactor` | `[refactor]` |
| `perf` | `[perf]` |
| `test` | `[test]` |
| `build` | `[build]` |
| `ci` | `[ci]` |
| `chore` | `[chore]` |
| `revert` | `[revert]` |

标题格式为 `[前缀] 中文变更目标`。正文根据本次差异生成，必须包含问题或需求背景、当前表现、本次目标、可核验的验收标准和涉及路径。不要虚构用户、线上事故、复现结果或测试证据。

创建接口为：

```http
POST /api/issues
Content-Type: application/json

{
  "title": "[bug] 修复登录问题",
  "body": "背景、当前表现、目标、验收标准和涉及路径",
  "assigneeIds": [12],
  "labelIds": [],
  "milestoneId": null
}
```

示例中的 `12` 代表当前用户 ID；实际请求必须保持 `GET /api/auth/me` 返回 ID 的原始类型，不要自行转为字符串或数字。`assigneeIds` 必须只包含该当前用户 ID。记录成功响应中的 Issue 编号。请求超时或响应不明确时，不要直接重试创建；先按完整标题重新查询，确认没有创建成功后才可重试，避免重复 Issue。

## 4. 判断关联标签

读取所选或新建 Issue 的目标与验收标准，逐项对照本次提交差异：

- 两者均被本次改动覆盖：视为完全解决，标签为 `#a<编号>`。
- 任一目标或验收标准未被覆盖：视为未完全解决，先向用户列出未解决内容，标签为 `#<编号>`。

不要把测试是否通过加入“完全解决”的定义；测试和检查仍按仓库规则独立执行。证据不足以证明某项目标或验收标准已覆盖时，将该项视为未覆盖。

## 5. 生成提交信息

提交信息采用中文 Conventional Commits：

```text
<type>(<scope>): <中文摘要> <Issue 标签>
```

例如：

```text
fix(mobile): 修复登录异常 #a4
feat(route): 增加路线筛选能力 #12
```

要求：

- `type` 只能使用映射表中的类型，并与改动性质一致。
- `scope` 使用稳定、简短的客户端或业务域名称；确实没有合理范围时可省略括号部分。
- 摘要必须使用中文，准确描述本次提交的结果，不使用“更新代码”等空泛措辞。
- Issue 标签必须是提交信息最后一项。完全解决用 `#a<编号>`，未完全解决用 `#<编号>`。
- 一个提交只关联本次选定或创建的一个 Issue。若本次范围实际跨越互不相关目标，应先拆分提交。

## 6. 验证并提交

1. 按仓库规则完成与本次范围相称的检查。新增或修改 API 时必须按仓库要求使用 `curl` 验证。
2. 检查最终差异，确认没有密钥、生成物误改、调试代码或范围外文件。
3. 使用显式路径逐一暂存本次文件。
4. 复查 `git diff --cached --stat` 和 `git diff --cached`；若出现范围外内容，停止，不要提交。
5. 使用生成的单条中文提交信息执行非交互式 `git commit`。
6. 提交后检查 `git show --stat --oneline HEAD`，向用户报告提交哈希、提交信息、关联 Issue、完全或部分覆盖结论、验证结果，以及仍留在工作区但未提交的改动。

不得自动推送、合并、关闭 Issue、修改 Issue 状态或添加 Issue 评论。
